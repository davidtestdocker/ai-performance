## 要解決的問題

看到程式很忙，如何知道數字量對了，以及 CPU、等待和資料移動各占多少？

前置：無；從此階段重新開始。

## 必要觀念

wall time 是經過時間；CPU time 是程序實際用 CPU 的累計時間。程序 100% 通常約占一個邏輯 CPU，整機利用率還取決於 CPU 數量。利用率是線索，不能單獨證明瓶頸。

## 逐步練習

以下按多次教學進行，每次只取一個操作，先講清楚再等待結果。未確認環境前不預寫安裝或訓練命令。

1. 確認目前所在的 Linux 主機、CPU／記憶體／磁碟與 Python；每次只查本步需要的資訊。
2. 自己寫最小 CPU 計算與等待對照，先核對答案，再量 wall time 與 CPU time。
3. 讀懂既有熱擴散程式的陣列、更新與邊界；加小網格逐元素參考答案，總和只作合理性檢查。
4. 把同一次工作負載的程序指標與正確性輸出對齊，解釋程序與整機 CPU 的差異。
5. GPU 環境確認後，用一個張量運算觀察非同步、暖機、主機同步計時與 CUDA event 的差異。

## 可驗收成果

能重跑 CPU 正確性與計時對照；有同次執行的負載輸出和程序指標；GPU 量測清楚分開端到端與裝置時間。

每個實驗保存目的與假設、環境／輸入、命令、正確性、原始數據、圖與判讀。調整採用或放棄都需理由；用小變化驗證可獨立理解。

## 面試練習

程序 100% CPU，整機仍然閒置，是否矛盾？GPU 利用率高能證明算力已用滿嗎？

## 第一步：確認目前 Linux 主機

**目的與影響：**在已連線的 Linux VM 終端執行，先辨識正在操作的主機、核心與 CPU 架構，避免把不同主機的結果混在一起。`uname` 顯示系統身分，`-a` 顯示完整欄位；此命令唯讀，不建立檔案或改服務。

**待執行指令：**

```bash
uname -a
```

**如何判讀：**依序辨認 Linux、主機名稱、核心版本及末段架構。實際值以回傳輸出為準。收到輸出後才記錄結果並給下一個操作。
