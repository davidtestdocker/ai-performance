[路線](ROADMAP.md)｜目標：判斷數字是否可信，能從 CPU、記憶體、I/O 與 GPU 指標提出可驗證的瓶頸假設。

## 本模組使用的機器

這個模組要分辨程式真的慢在哪裡，還是量測方式讓數字失真。
效能工程面試與實務分析都需要先說清楚數字來自哪台機器、使用什麼資源，最後交付可核對的計時與瓶頸判讀。

本專案的「控制節點」是台灣的 VM `instance-20260923-104239`，工作樹位於 `/root/ai-performance`；目前的 CPU 與記憶體盤點由這台 VM 的終端機執行。
之後需要 GPU 計時時，使用東京的 `compute-gpu01`（規劃配備一張 NVIDIA L4）。
兩台機器的用途與先前查得的資源狀態見[現有機器安排](INFRASTRUCTURE.md)，實驗時仍須核對當下狀態。

## 學習大綱

量測單位與指標 → Linux/硬體拓撲盤點 → CPU/GPU 正確計時 → 三類瓶頸的系統觀察 → 寫出可被推翻的診斷。

## 先理解

區分延遲、吞吐、利用率、頻寬、峰值顯存、端到端時間與 kernel 時間；理解暖機、CUDA 非同步、page cache、時鐘變動和共用資源如何污染結果。畫出一個訓練 step 的 CPU 資料準備 → H2D → GPU 前反向 → optimizer → checkpoint 路徑。

## 實作順序

1. 盤點 `lscpu`、NUMA、記憶體、磁碟、網卡、GPU、驅動與 CUDA；用 `nvidia-smi` 記錄 GPU 型號、顯存、時脈、功率、溫度與錯誤狀態，可用時再用 DCGM 收集健康／profiling 欄位。記下無法讀取的項目，不補猜值。[NVIDIA DCGM](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)
2. 用可核對答案的小型 CPU 工作測量 wall time 與 CPU time；再用 GPU 工作比較未同步主機計時、同步主機計時和 CUDA event，說明差異。[PyTorch CUDA 計時](https://docs.pytorch.org/docs/stable/notes/cuda.html)
3. 對 CPU 密集、記憶體密集和 I/O 密集的簡單工作各做一次觀察，收集 `pidstat`、`iostat`、`vmstat`、`perf stat`（權限允許時）與 GPU 記憶體／活動。不要把 GPU utilization 單一數字直接當成吞吐。[Linux workload tracing](https://docs.kernel.org/admin-guide/workload-tracing.html)
4. 對每個工作先預測瓶頸，再寫出哪一個觀察能推翻預測。

## 做完留下的成果

有一份含 GPU 健康／時脈條件的環境快照、三種工作負載的原始時間與系統指標，以及一頁「數字可信度」報告；能解釋同步前後計時為何不同，並指出至少一個量測陷阱。資料與報告歸入 `results/01/`、`reports/01.md`，未實作前不預建假結果。

## CPU 計時：wall time 與 CPU time

wall time 是從開始到完成實際經過的時間；CPU time 是程式在 CPU 上執行所累積的時間。
在控制節點執行[計時程式](../project/01/cpu_timing.py)：它先計算 `0` 到 `4,999,999` 的平方和，與公式答案核對，再量這段工作的 wall time 與 CPU time；接著等待半秒，量同樣兩個時間作對照。
程式只使用 Python 標準函式庫，不讀寫檔案或修改服務。

**已執行指令（在控制節點 VM 的 `/root/ai-performance`）：**

```bash
python3 project/01/cpu_timing.py
```

**實際結果：**

```text
平方和正確：41666654166667500000
CPU 計算：wall=0.462751s cpu=0.457627s
等待半秒：wall=0.500201s cpu=0.000059s
```

**判讀：**平方和與公式答案一致，計算工作正確完成。

| 工作 | wall time | CPU time | 意義 |
|---|---:|---:|---|
| 計算 500 萬項平方和 | 0.462751 秒 | 0.457627 秒 | 程式大部分經過時間都在使用 CPU。 |
| 等待半秒 | 0.500201 秒 | 0.000059 秒 | 等待算入經過時間，幾乎不消耗 CPU 計算時間。 |

**第二次執行同一指令的實際結果：**

```text
平方和正確：41666654166667500000
CPU 計算：wall=0.484902s cpu=0.470027s
等待半秒：wall=0.500145s cpu=0.000047s
```

| CPU 計算 | 第一次 | 第二次 | 差值 |
|---|---:|---:|---:|
| wall time | 0.462751 秒 | 0.484902 秒 | 第二次多 0.022151 秒 |
| CPU time | 0.457627 秒 | 0.470027 秒 | 第二次多 0.012400 秒 |

兩次等待段的 wall time 都約 0.5 秒、CPU time 都接近 0；相同程式的 CPU 計算時間則有小幅變動。

## 系統指標：先看控制節點狀態

`vmstat` 會同時顯示 CPU 使用情形、記憶體與工作排隊等系統指標。先在沒有刻意啟動測試工作時取得輸出，作為接下來觀察 CPU 工作時的對照。

**目的與影響：**在控制節點 VM 查看統計；指令只讀取資訊，不修改檔案或服務。`vmstat 1 4` 中的 `1` 是秒數間隔，`4` 是輸出筆數。第一筆是自開機以來的平均值；後三筆各代表前一秒的情形，用後三筆看目前狀態。

**已執行指令（在控制節點 VM）：**

```bash
vmstat 1 4
```

**欄位介紹：**這些欄位描述的是整台 VM，不是某個程式。

| 欄位 | 白話意思 | 這次怎麼看 |
|---|---|---|
| `r`、`b` | `r` 是取樣當下正在執行或等 CPU 的工作數；`b` 是等 I/O 等資源而停住的工作數。 | `r` 看是否持續有工作排隊，`b` 看是否有工作持續卡住；單筆數值不代表整秒都如此。 |
| `swpd`、`free`、`buff`、`cache` | 已使用的交換空間、閒置記憶體、緩衝區與快取，預設以 KiB 顯示。 | 這次先看 `swpd`；`free` 不能單獨當作可供程式使用的記憶體總量。 |
| `si`、`so` | 每秒從交換空間讀入、寫出的資料量，預設以 KiB/s 顯示。 | 持續大於 0 才需要進一步追查交換記憶體活動。 |
| `bi`、`bo` | 每秒從區塊裝置讀入、寫出的資料區塊數。區塊裝置通常是磁碟。 | 看讀寫活動是否出現；這裡不據此推算磁碟吞吐量。 |
| `in`、`cs` | 每秒中斷次數、每秒工作切換次數。 | 可觀察系統活動量，這次不以單一數值判定異常。 |
| `us`、`sy`、`id` | CPU 時間中用於程式、核心、閒置的百分比。 | 先看 `id`，再看忙碌時間落在 `us` 還是 `sy`。 |
| `wa`、`st`、`gu` | CPU 時間中等待 I/O、被虛擬化平台取走、執行客體 VM 的百分比。 | 這台本身是 VM，留意 `st`；`wa` 用來觀察 I/O 等待。 |

**實際結果：**

```text
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 3  0      0 2316904   3136 646428    0    0  1112    18  422    2  3  2 95  0  0  0
 3  0      0 2316904   3136 646468    0    0     0     6  453  559  1  2 96  0  0  0
 0  0      0 2316652   3136 646484    0    0     0     4  580  598  2  4 93  0  1  0
 0  0      0 2316652   3136 646484    0    0     0     0  479  522  1  2 97  0  1  0
```

**判讀：**第一筆是自開機以來的平均值，不用來代表這三秒的即時狀態。後三筆中，`id` 為 93%～97%，表示 CPU 大多閒置；`wa` 均為 0%，沒有觀察到 CPU 等待 I/O 的時間；`si`、`so` 均為 0，沒有觀察到交換記憶體的讀寫。`r` 從 3 降至 0，表示取樣當下可執行的工作數有變動，不能只憑單一秒判定持續排隊。這組數據作為未刻意啟動測試工作時的對照。

## 系統指標：確認程序與磁碟工具

目前的 `vmstat` 已能看到整台 VM 的 CPU、記憶體與 I/O 概況；要辨認後續工作負載本身用了多少 CPU，還需要依程序查看的工具。`pidstat` 可定期列出程序的 CPU 等用量，`iostat` 可查看磁碟裝置的 I/O，讓系統總量與程序、磁碟的數字互相對照。

**實際結果：**控制節點已安裝 `pidstat` 與 `iostat`，可分別觀察個別程序與磁碟裝置的指標。

## CPU 工作負載：準備二維熱擴散程式

前面的 `vmstat` 只描述沒有刻意啟動工作時的整機狀態；要觀察程序使用 CPU 的過程，需要一個執行時間足夠、結果可核對的工作。二維熱擴散把方格中的數值反覆依上下左右鄰點更新，這類「每格讀鄰近資料」的運算也見於影像處理與科學計算。這裡用固定的 1024×1024 方格與 3000 輪更新；中央熱源的總和應保持接近 65536，程式會印出誤差與 `PASS`／`FAIL`。它是公開可重跑的代表性運算，並非任何公司的實際業務負載。

[程式來源](../project/01/heat2d_cpu.cpp) 位於控制節點工作樹。`g++` 是 C++ 編譯器：它讀取來源檔，產生 VM 可執行的檔案。先編譯，再於下一步執行及量測，避免把編譯時間混入運算時間。

**目的與影響：**在控制節點 VM 的 `/root/ai-performance` 執行下列指令。`-std=c++17` 指定語言版本，`-O2` 啟用一般最佳化，`-o` 指定輸出檔 `/tmp/heat2d_cpu`。這一步只在 `/tmp` 建立或取代該執行檔，不執行工作負載，不修改服務或雲端資源；編譯成功通常沒有終端輸出。

**已執行指令（在控制節點 VM）：**

```bash
g++ -std=c++17 -O2 project/01/heat2d_cpu.cpp -o /tmp/heat2d_cpu
```

**實際結果：**終端沒有印出編譯訊息；`/tmp/heat2d_cpu` 已產生且可執行，檔案大小 17400 bytes，修改時間晚於來源檔。編譯完成，尚未執行工作負載。

## CPU 工作負載：執行與正確性核對

編譯後的程式會在控制節點使用單一 CPU 執行緒反覆更新方格。先單獨執行，確認輸入規模、計算時間與總和核對都如預期，再在工作運行期間觀察系統指標。

**目的與影響：**在控制節點 VM 執行 `/tmp/heat2d_cpu`。程式在記憶體中建立兩份 1024×1024 方格，更新 3000 輪，結束時印出總和、與 65536 的差值、運算秒數及 `PASS`／`FAIL`；不建立資料檔、不修改服務或雲端資源。運行期間會占用約一個邏輯 CPU，完成後釋放記憶體。

**已執行指令（在控制節點 VM）：**

```bash
/tmp/heat2d_cpu
```

**輸出欄位：**`grid` 與 `steps` 核對輸入規模；`sum`、`expected`、`abs_error` 核對計算結果；`compute_seconds` 是更新方格的經過時間；`validation=PASS` 代表誤差在程式設定範圍內，`FAIL` 則需停止分析效能並先修正計算。

**實際結果：**

```text
grid=1024x1024 steps=3000
sum=65535.939468 expected=65536.000000 abs_error=0.060532
compute_seconds=26.348529 validation=PASS
```

**判讀：**程式完成固定的 1024×1024 方格、3000 輪更新；總和與 65536 的差值為 0.060532，在程式允許的 0.5 範圍內，因此 `validation=PASS`。更新方格的經過時間為 26.348529 秒，足以在執行期間取多筆程序 CPU 樣本。
